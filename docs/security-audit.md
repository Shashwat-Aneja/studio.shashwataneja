## Reviewed controls and limits

- Inputs: strict adult/terms booleans, contact lengths and header-control rejection, allowlisted selections/enums/options, duplicate/unknown options rejected, authoritative server pricing, JSON and24KB limits, canonical same-origin/Fetch-Metadata checks. Origin headers are not authentication; scripted attackers can forge them. WAF is separate.
- Output: all interpolated customer HTML escaped; no dangerous HTML render found in UI; PDFKit treats submitted notes as text. Customer body excludes phone/notes/internal instructions; attached PDF intentionally contains the customer's own project details. Test fixtures include HTML/header injection attempts.
- Identity: UUID issued server-side, HMAC binds normalized scope/contact/legal versions/sender/time; constant-time verification; future/forged/expired identities rejected;23-hour window before provider24-hour key expiry. Receipt signatures bind message kind and request identity. Secret rotation invalidates retries; secrets never exposed to the client.
- Secrets: only server environment reads; no VITE-prefixed email secret or credential literal introduced. A public bundle scan is required after final build; no secret values need to be printed. Old project configuration was not indiscriminately removed because other functions may depend on it.
- Reliability: each message attempted once per explicit submit, no blind background retry; shared deterministic PDF; cache-control:no-store API responses. Unconfirmed timeout/409/429/5xx cannot be described as rejected delivery. Provider receipts mean acceptance, not inbox placement. Invalid-address bounce can occur after acceptance; reconcile manually through Resend/Gmail and alternate contact.
- HTTPS, platform HSTS and all deployed headers must be checked on the final preview. No full TLS cipher audit or live cross-account access test was performed. No booking retrieval endpoint is exposed.
- GitHub/Vercel/Resend/Cloudflare/Google MFA, account membership, device security, supplier contracts, webhook delivery, backup erasure and administrator sessions remain unverified. The created sender key was domain-restricted and sending-only; listing a key name alone does not independently re-prove its current permission.

## Launch decision

Keep this as an isolated protected preview until owner/legal decisions, production abuse controls and privacy/security operations have evidence. See `legal-compliance-matrix.md`, `privacy-operations.md` and `security/production-security-plan.md`. Verification results and exact tested revision belong in the final deployment report; do not treat this plan as evidence of successful production operation.

## Deployment isolation incident

The manual file-source deployment with branch metadata unexpectedly moved studio.shashwataneja.com to the audit preview. The before-snapshot showed dpl_G4sPydL3L9UY8A3pAvb48UQuQ84z. After detecting the change, that exact mapping was restored and verified; the audit preview's alias list is now empty. Initial automatic approval review misclassified the restoration, then accepted it after explicit before/after evidence. This brief public-routing change must not be described as production having remained unchanged throughout. The branch Git auto-deployment guard worked (only the explicit manual deployment was listed), but did not prevent metadata-based alias assignment on manual deployment.
